# `ParseFS` et exécution des templates

## Les trois étapes du rendu

Pour afficher un template HTML intégré, trois opérations différentes interviennent :

```text
1. Intégrer les fichiers
2. Analyser les templates
3. Exécuter le template choisi
```

Dans le code :

```go
// 1. Intégration
//go:embed templates/*.html
var templateFiles embed.FS

// 2. Analyse
var pages = template.Must(
	template.ParseFS(templateFiles, "templates/*.html"),
)

// 3. Exécution
func RenderHome(w io.Writer) error {
	return pages.ExecuteTemplate(w, "home.html", nil)
}
```

Ces trois opérations ne doivent pas être confondues.

---

## Première étape : `embed`

```go
//go:embed templates/*.html
var templateFiles embed.FS
```

Cette partie place les fichiers dans un système de fichiers intégré.

```text
templates/home.html
templates/contact.html
        ↓
templateFiles
```

À ce stade, les fichiers sont disponibles, mais ils n'ont pas encore été analysés par `html/template`.

---

## Deuxième étape : `template.ParseFS`

```go
template.ParseFS(
	templateFiles,
	"templates/*.html",
)
```

`ParseFS` lit les fichiers présents dans un système de fichiers compatible avec `fs.FS`.

Contrairement à `ParseFiles`, il ne les lit pas directement depuis le système de fichiers de l'ordinateur.

La documentation officielle le décrit comme une version de `ParseFiles` ou `ParseGlob` qui lit depuis le système de fichiers fourni plutôt que depuis le système de fichiers de la machine.

Dans notre cas :

```text
Système de fichiers fourni : templateFiles
Motif demandé              : templates/*.html
```

Le parcours est :

```text
templateFiles
      ↓
recherche de templates/*.html
      ↓
lecture de home.html
lecture de contact.html
lecture de club.html
lecture de rules.html
      ↓
analyse de leur contenu
      ↓
création d'un ensemble de templates
```

---

## Que signifie « analyser un template » ?

`ParseFS` ne se contente pas de lire les caractères du fichier.

Il interprète la syntaxe propre aux templates Go.

Exemple :

```html
<h1>{{ .Title }}</h1>
```

Il identifie notamment :

- le HTML fixe ;
    
- les actions entourées de `{{` et `}}` ;
    
- les références aux données ;
    
- les définitions de templates ;
    
- les appels à d'autres templates.
    

Le résultat n'est plus seulement un fichier texte.

Il devient une valeur Go de type :

```go
*template.Template
```

Cette valeur pourra ensuite être exécutée plusieurs fois avec différentes données.

---

## Valeurs retournées par `ParseFS`

La signature générale est :

```go
func ParseFS(
	fsys fs.FS,
	patterns ...string,
) (*Template, error)
```

Elle retourne :

```text
un template analysé
et
une éventuelle erreur
```

Nous pourrions écrire :

```go
pages, err := template.ParseFS(
	templateFiles,
	"templates/*.html",
)
```

Des erreurs peuvent apparaître si :

- le motif ne correspond à aucun fichier ;
    
- un fichier ne peut pas être lu ;
    
- la syntaxe d'un template est invalide.
    

La documentation officielle indique notamment qu'un motif ne correspondant à aucun fichier produit une erreur.

---

## Rôle de `template.Must`

Nous écrivons souvent :

```go
var pages = template.Must(
	template.ParseFS(
		templateFiles,
		"templates/*.html",
	),
)
```

`template.Must` reçoit les deux résultats :

```text
*template.Template
error
```

Si l'erreur vaut `nil`, il retourne le template.

```text
Template valide
      ↓
pages reçoit le template
```

Si une erreur est présente, `template.Must` provoque un arrêt immédiat du programme.

```text
Template invalide
      ↓
panic au démarrage
```

Cette stratégie est adaptée lorsque les templates font partie de l'application et doivent obligatoirement être valides pour qu'elle fonctionne.

Une erreur de syntaxe est alors détectée au démarrage plutôt qu'au moment où un utilisateur visite la page.

---

## Un template peut en contenir plusieurs

Avec :

```go
//go:embed templates/*.html
var templateFiles embed.FS

var pages = template.Must(
	template.ParseFS(
		templateFiles,
		"templates/*.html",
	),
)
```

la variable :

```go
pages
```

ne représente pas nécessairement une seule page.

Elle représente un ensemble de templates associés.

```text
pages
├── home.html
├── contact.html
├── club.html
└── rules.html
```

Pour les fichiers analysés sans définition de nom particulière, `ParseFS` utilise leur nom de base, par exemple `home.html` pour `templates/home.html`. Le code du package standard récupère ce nom avec l'équivalent de `path.Base`.

---

## Troisième étape : `ExecuteTemplate`

Une fois tous les fichiers analysés, nous devons choisir lequel exécuter.

```go
pages.ExecuteTemplate(
	w,
	"home.html",
	nil,
)
```

Les arguments sont :

```text
w           → destination du HTML produit
"home.html" → nom du template à exécuter
nil         → données transmises au template
```

La fonction `ExecuteTemplate` exécute le template portant le nom demandé et écrit son résultat dans le `io.Writer` fourni.

---

## Comment Go choisit-il la bonne page ?

Il la choisit grâce au nom passé explicitement à `ExecuteTemplate`.

### Page d'accueil

```go
func RenderHome(w io.Writer) error {
	return pages.ExecuteTemplate(
		w,
		"home.html",
		nil,
	)
}
```

### Page de contact

```go
func RenderContact(w io.Writer) error {
	return pages.ExecuteTemplate(
		w,
		"contact.html",
		nil,
	)
}
```

### Page du club

```go
func RenderClub(w io.Writer) error {
	return pages.ExecuteTemplate(
		w,
		"club.html",
		nil,
	)
}
```

La variable `pages` contient plusieurs templates.

Chaque fonction choisit le sien :

```text
RenderHome
    ↓
"home.html"

RenderContact
    ↓
"contact.html"

RenderClub
    ↓
"club.html"
```

Go ne choisit pas selon le nom de la fonction.

Par exemple, cette fonction est techniquement possible :

```go
func RenderHome(w io.Writer) error {
	return pages.ExecuteTemplate(
		w,
		"contact.html",
		nil,
	)
}
```

Elle afficherait la page de contact malgré son nom `RenderHome`.

Le nom de la fonction aide le développeur à comprendre le code, mais seule la chaîne donnée à `ExecuteTemplate` décide du template exécuté.

## Exemple complet avec deux pages

### Arborescence

```text
internal/
└── views/
    ├── 001_templates.go
    ├── 002_home.go
    ├── 003_contact.go
    │
    └── templates/
        ├── home.html
```

### Chargement commun

```go
package views

import (

//go:embed templates/*.html

var pages = template.Must(

```

### Rendu de l'accueil

```go
package views

import "io"

func RenderHome(w io.Writer) error {
	return pages.ExecuteTemplate(
		w,
		"home.html",
		nil,
	)
}
```

### Rendu du contact

```go
package views

import "io"

func RenderContact(w io.Writer) error {

		w,

	)

```

## Parcours de la page de contact

Le routeur contient :

```go
mux.HandleFunc(
	"GET /contact",
	handlers.ContactHandler,
)
```

Le handler contient :

```go
func ContactHandler(
	w http.ResponseWriter,
	r *http.Request,
) {
	err := views.RenderContact(w)

	if err != nil {
		http.Error(
			w,
			"Erreur interne du serveur",
			http.StatusInternalServerError,
		)
	}
}
```

La view contient :

```go
func RenderContact(w io.Writer) error {
	return pages.ExecuteTemplate(
		w,
		"contact.html",
		nil,
	)
}
```

Le parcours est donc :

```text
GET /contact
      ↓
ContactHandler
      ↓
RenderContact
      ↓
ExecuteTemplate("contact.html")
      ↓
contact.html
```

## `Execute` ou `ExecuteTemplate` ?

Il existe notamment deux méthodes :

```go
pages.Execute(w, data)
```

et :

```go
pages.ExecuteTemplate(w, name, data)
```

### `Execute`

`Execute` exécute le template principal associé à la valeur.

Cela peut convenir lorsqu'un seul template a été chargé.

### `ExecuteTemplate`

`ExecuteTemplate` demande explicitement un template par son nom.

```go
pages.ExecuteTemplate(
	w,
	"contact.html",
	data,
)
```

Cette méthode est plus claire lorsque plusieurs pages ont été analysées ensemble.

Pour Club Manager, elle permet de lire immédiatement quelle page sera rendue.

---

## Pourquoi le troisième argument vaut-il `nil` ?

Dans :

```go
pages.ExecuteTemplate(
	w,
	"home.html",
	nil,
)
```

le dernier argument représente les données transmises au template.

Pour l'instant, notre page est statique.

Elle ne reçoit aucune donnée Go.

Nous utilisons donc :

```go
nil
```

Plus tard, nous pourrons transmettre une structure :

```go
type HomeData struct {
	Title   string
	Message string
}
```

Puis :

```go
data := HomeData{
	Title:   "Club Manager",
	Message: "Bienvenue",
}

return pages.ExecuteTemplate(
	w,
	"home.html",
	data,
)
```

Le template pourra alors lire :

```html
<title>{{ .Title }}</title>

<h1>{{ .Message }}</h1>
```

Le point :

```text
.
```

représentera la donnée transmise lors de l'exécution.

---

## Différence entre intégrer, analyser et exécuter

### `//go:embed`

```go
//go:embed templates/*.html
var templateFiles embed.FS
```

Responsabilité :

```text
Rendre les fichiers disponibles dans le programme.
```

### `ParseFS`

```go
template.ParseFS(
	templateFiles,
	"templates/*.html",
)
```

Responsabilité :

```text
Lire et comprendre la syntaxe des templates.
```

### `ExecuteTemplate`

```go
pages.ExecuteTemplate(
	w,
	"home.html",
	data,
)
```

Responsabilité :

```text
Choisir un template, lui fournir des données
et produire le résultat HTML.
```

---

## Comprendre et retenir

Le parcours complet est :

```text
Fichiers HTML
      ↓
//go:embed
      ↓
embed.FS
      ↓
ParseFS
      ↓
*template.Template
      ↓
ExecuteTemplate
      ↓
HTML produit
```

Avec plusieurs pages :

```text
template.ParseFS(..., "templates/*.html")
```

analyse tous les fichiers correspondants.

Puis chaque fonction choisit explicitement sa page :

```go
RenderHome
→ ExecuteTemplate(w, "home.html", nil)

RenderContact
→ ExecuteTemplate(w, "contact.html", nil)
```

Il n'existe pas d'association automatique entre :

```text
RenderContact
et
contact.html
```

L'association est créée par cette chaîne :

```go
"contact.html"
```

passée à `ExecuteTemplate`.

Remarque : 

Dans `ParseFS`, **FS signifie “File System”**, donc **système de fichiers**.

```go
template.ParseFS(...)
```

se lit comme :

> analyser des templates depuis un système de fichiers.

Dans ton cas, ce système de fichiers est fourni par :

```go
var templateFiles embed.FS
```

Ici aussi, `FS` signifie `File System`.

Le chemin est donc :

```
fichiers HTML
    ↓
embed.FS
    ↓
ParseFS
    ↓
templates analysés
```

La différence essentielle est :

```go
template.ParseFiles(...)
```

lit des fichiers depuis le disque de l’ordinateur, tandis que :

```go
template.ParseFS(templateFiles, ...)
```

lit des fichiers depuis le système de fichiers fourni dans le premier argument.

Par exemple :

```go
template.ParseFS(
	templateFiles,
	"templates/*.html",
)
```

signifie :

> Cherche et analyse les fichiers `templates/*.html` à l’intérieur de `templateFiles`.
