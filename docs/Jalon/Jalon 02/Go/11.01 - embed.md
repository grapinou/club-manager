# Intégrer des fichiers avec `embed`

## Le problème des fichiers externes

Une application Go peut lire un fichier présent sur le disque.

Exemple :

```go
template.ParseFiles("templates/home.html")
```

Le programme doit alors retrouver ce fichier au moment de son exécution.

Le chemin dépend du dossier courant depuis lequel la commande a été lancée.

Une organisation comme celle-ci peut donc poser des questions :

```text
club-manager/
├── cmd/server/main.go
└── internal/views/templates/home.html
```

Depuis quel dossier le programme est-il lancé ?

```bash
go run ./cmd/server
```

Depuis quel dossier les tests sont-ils exécutés ?

```bash
go test ./...
```

Où se trouvera le fichier HTML lorsque l'application sera installée sur une autre machine ?

Le package `embed` apporte une réponse à ce problème.

---

## Rôle de `embed`

Le package standard `embed` permet d'intégrer des fichiers dans le programme Go lors de la compilation.

```text
Fichier présent dans le projet
             ↓
Compilation du programme
             ↓
Fichier intégré au programme
             ↓
Disponible pendant l'exécution
```

La documentation officielle indique que `//go:embed` initialise une variable avec le contenu de fichiers lus depuis le dossier du package ou ses sous-dossiers au moment de la compilation.

Exemple :

```go
package views

import "embed"

//go:embed templates/home.html
var homeFiles embed.FS
```

La variable :

```go
homeFiles
```

contient alors un petit système de fichiers intégré au programme.

---

## Que représente `embed.FS` ?

`FS` signifie ici :

```text
File System
```

Un `embed.FS` représente un système de fichiers en lecture seule.

Il peut contenir :

- un fichier ;
    
- plusieurs fichiers ;
    
- une arborescence de fichiers.
    

Exemple :

```go
//go:embed templates/home.html
var homeFiles embed.FS
```

La variable contient :

```text
homeFiles
└── templates/
    └── home.html
```

Avec plusieurs fichiers :

```go
//go:embed templates/*.html
var templateFiles embed.FS
```

elle pourrait contenir :

```text
templateFiles
└── templates/
    ├── home.html
    ├── club.html
    ├── contact.html
    └── rules.html
```

`embed.FS` respecte l'interface de système de fichiers de Go et peut donc être utilisé par des packages qui savent lire un `fs.FS`, notamment `html/template`.

---

## Comprendre la directive `//go:embed`

Cette ligne ressemble à un commentaire :

```go
//go:embed templates/home.html
```

Mais elle est reconnue spécialement par l'outil de compilation Go.

Elle signifie :

> Prends le fichier `templates/home.html` et intègre-le dans la variable déclarée juste après.

```go
//go:embed templates/home.html
var homeFiles embed.FS
```

La directive doit être associée à une déclaration de variable.

La documentation précise qu'elle doit précéder cette déclaration et que seuls des commentaires de ligne ou des lignes vides peuvent éventuellement se trouver entre les deux.

L'écriture la plus claire reste donc :

```go
//go:embed templates/home.html
var homeFiles embed.FS
```

---

## Depuis quel dossier le chemin est-il calculé ?

Le chemin donné à `//go:embed` est relatif au dossier du package Go contenant la directive.

Avec cette structure :

```text
internal/
└── views/
    ├── 001_home.go
    └── templates/
        └── home.html
```

et cette directive placée dans `001_home.go` :

```go
//go:embed templates/home.html
var homeFiles embed.FS
```

Go cherche :

```text
internal/views/templates/home.html
```

Il ne cherche pas depuis :

```text
cmd/server/
```

Il ne cherche pas non plus depuis le dossier dans lequel la commande `go run` est saisie.

Le point de départ est le dossier du package contenant la directive.

---

## `embed` associe-t-il une page à une fonction ?

Non.

Cette directive :

```go
//go:embed templates/home.html
var homeFiles embed.FS
```

fait uniquement ceci :

```text
home.html
    ↓
intégré dans
    ↓
homeFiles
```

Elle ne crée pas automatiquement :

```text
HomeHandler → home.html
```

Elle ne connaît pas :

- les routes HTTP ;
    
- les handlers ;
    
- les fonctions `RenderHome` ;
    
- le rôle métier de la page.
    

`embed` rend seulement le fichier disponible dans le programme.

L'association avec une fonction sera faite plus tard avec :

```go
template.ParseFS(...)
```

puis :

```go
ExecuteTemplate(...)
```

---

## Que se passe-t-il avec `contact.html` ?

Imaginons cette structure :

```text
templates/
├── home.html
└── contact.html
```

Mais la directive reste :

```go
//go:embed templates/home.html
var templateFiles embed.FS
```

Seul `home.html` est intégré.

Le contenu réel est alors :

```text
templateFiles
└── templates/
    └── home.html
```

`contact.html` existe dans le projet, mais il n'existe pas dans ce système de fichiers intégré.

Une tentative de lecture de :

```text
templates/contact.html
```

échouera.

---

## Intégrer plusieurs pages

Pour intégrer toutes les pages HTML du dossier :

```go
//go:embed templates/*.html
var templateFiles embed.FS
```

Le caractère :

```text
*
```

signifie ici :

> Tous les fichiers correspondant à ce motif.

Avec :

```text
templates/*.html
```

Go inclut les fichiers HTML directement présents dans le dossier `templates`.

```text
templates/home.html
templates/contact.html
templates/club.html
templates/rules.html
```

Chaque motif `//go:embed` doit correspondre à au moins un fichier ou à un dossier non vide, sinon la compilation échoue.

---

## Un seul système de fichiers ou un par page ?

### Un système de fichiers par page

```go
//go:embed templates/home.html
var homeFiles embed.FS

//go:embed templates/contact.html
var contactFiles embed.FS
```

Cette approche est explicite.

Cependant, elle devient répétitive lorsque le nombre de pages augmente.

---

### Un système de fichiers commun

```go
//go:embed templates/*.html
var templateFiles embed.FS
```

Cette approche centralise les templates :

```text
templateFiles
├── home.html
├── contact.html
├── club.html
└── rules.html
```

Les fonctions de rendu sélectionneront ensuite le bon fichier.

```text
RenderHome    → home.html
RenderContact → contact.html
RenderClub    → club.html
RenderRules   → rules.html
```

Pour la première page, utiliser un fichier unique permet de comprendre le mécanisme.

Lorsque plusieurs pages seront migrées, un système de fichiers commun deviendra probablement plus adapté.

---

## Conséquence d'une modification HTML

Les fichiers sont intégrés pendant la compilation.

Le déroulement est donc :

```text
Modification de home.html
          ↓
Nouvelle compilation
          ↓
Nouvelle version intégrée
```

Pendant le développement avec :

```bash
go run ./cmd/server
```

il faut arrêter et relancer le programme pour que la nouvelle version du fichier soit intégrée.

Le programme déjà lancé ne relit pas automatiquement le fichier HTML présent sur le disque.

---

## Avantages de `embed`

### Programme autonome

Les templates sont intégrés dans le programme.

Il n'est pas nécessaire de copier séparément :

```text
templates/home.html
```

à côté de l'exécutable.

---

### Chemins plus fiables

Le fonctionnement ne dépend pas du dossier depuis lequel l'application est lancée.

---

### Tests plus simples

Les tests et le serveur utilisent les mêmes fichiers intégrés.

---

### Déploiement simplifié

Le programme compilé contient ses templates.

Il reste possible que l'application ait d'autres dépendances externes, comme une base de données ou un fichier de configuration, mais les templates intégrés ne doivent pas être distribués séparément.

---

## Limites de `embed`

Les fichiers intégrés sont en lecture seule.

L'application ne peut pas modifier durablement :

```text
home.html
```

à l'intérieur de l'exécutable.

Toute modification nécessite :

1. de modifier le fichier source ;
    
2. de reconstruire le programme.
    

`embed` convient donc bien aux ressources faisant partie du code de l'application :

- templates ;
    
- fichiers CSS ;
    
- images fixes ;
    
- petits fichiers statiques.
    

Il ne remplace pas une base de données pour les informations que l'application doit modifier pendant son fonctionnement.

---

## Comprendre et retenir

`embed` ne rend pas la page HTML.

Il rend le fichier disponible dans le programme.

```text
//go:embed
     ↓
intégration du fichier
     ↓
embed.FS
```

Cette directive :

```go
//go:embed templates/home.html
var homeFiles embed.FS
```

signifie :

```text
Intègre home.html dans homeFiles.
```

Cette directive :

```go
//go:embed templates/*.html
var templateFiles embed.FS
```

signifie :

```text
Intègre tous les fichiers HTML correspondants
dans templateFiles.
```

`embed` ne connaît ni les routes ni les handlers.

Il ne fait pas automatiquement :

```text
/contact → contact.html
```

Cette association sera explicitement réalisée par nos fonctions de rendu.
