# Passage des données au template

## Objectif

Une page HTML ne contient pas toujours uniquement du texte fixe.

Elle peut devoir afficher des informations provenant du programme Go :

- le titre de la page ;
    
- un message ;
    
- le nom d’un club ;
    
- une adresse ;
    
- des horaires ;
    
- une liste de membres ;
    
- plus tard, des informations provenant de la base de données.
    

Pour afficher ces informations, nous devons les faire circuler jusqu’au template.

Dans Club Manager, le parcours est :

```text
Handler
   ↓
Structure de données
   ↓
View
   ↓
Template HTML
```

Pour la page d’accueil :

```text
HomeHandler
   ↓
HomeData
   ↓
RenderHome
   ↓
001_home.html
```

---

## Avant le passage de données

Au départ, le texte était écrit directement dans le fichier HTML :

```html
<title>Club Manager</title>

<h1>Bienvenue sur Club Manager</h1>

<p>
    Une application destinée à faciliter la gestion d'une association.
</p>
```

Le template pouvait être exécuté sans recevoir de données :

```go
func RenderHome(w io.Writer) error {
	return homeTemplate.ExecuteTemplate(
		w,
		"001_home.html",
		nil,
	)
}
```

Le troisième argument valait :

```go
nil
```

Cela signifiait :

> Exécute le template sans lui transmettre de données.

---

## Limite de cette première version

Lorsque tout le contenu est écrit directement dans le HTML, la page est essentiellement statique.

```text
001_home.html
      ↓
Contient lui-même toutes les informations
```

Le code Go ne peut pas facilement choisir ou modifier :

- le titre ;
    
- le message principal ;
    
- la description ;
    
- les informations affichées selon la situation.
    

Pour rendre la page dynamique, les données doivent venir du programme Go.

---

# 1. Définir une structure de données

Nous créons une structure dédiée à la page d’accueil :

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

Cette structure décrit les informations dont le template a besoin.

```text
HomeData
├── Title
├── Heading
└── Description
```

Chaque champ possède un rôle précis.

### `Title`

```go
Title string
```

Correspond au titre affiché dans l’onglet du navigateur :

```html
<title>...</title>
```

### `Heading`

```go
Heading string
```

Correspond au titre principal de la page :

```html
<h1>...</h1>
```

### `Description`

```go
Description string
```

Correspond au texte de présentation :

```html
<p>...</p>
```

---

## Pourquoi utiliser une structure ?

Nous pourrions transmettre une seule chaîne de caractères :

```go
"Bienvenue sur Club Manager"
```

Mais une page contient généralement plusieurs informations.

Une structure permet de les regrouper :

```go
HomeData{
	Title:       "Club Manager",
	Heading:     "Bienvenue sur Club Manager",
	Description: "Une application destinée à faciliter la gestion d'une association.",
}
```

Elle constitue une description claire des données attendues par la page.

```text
Une page
   ↓
Une structure de données adaptée
```

---

## Une structure spécifique à chaque page

Plus tard, chaque page pourra avoir sa propre structure :

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

```go
type ContactData struct {
	Title string
	Email string
	Phone string
}
```

```go
type ClubData struct {
	Title        string
	Presentation string
}
```

Chaque template recevra seulement les données qui lui sont nécessaires.

---

# 2. Construire les données dans le handler

Le handler prépare une valeur de type `HomeData` :

```go
func HomeHandler(w http.ResponseWriter, r *http.Request) {
	data := views.HomeData{
		Title:       "Club Manager",
		Heading:     "Bienvenue sur Club Manager",
		Description: "Une application destinée à faciliter la gestion d'une association.",
	}

	err := views.RenderHome(w, data)

	if err != nil {
		http.Error(
			w,
			"Erreur interne du serveur",
			http.StatusInternalServerError,
		)
	}
}
```

La variable :

```go
data
```

contient toutes les informations destinées à la page d’accueil.

```text
data
├── Title       = "Club Manager"
├── Heading     = "Bienvenue sur Club Manager"
└── Description = "Une application destinée..."
```

---

## Pourquoi les données sont-elles créées dans le handler ?

Le handler coordonne la réponse à une requête HTTP.

Il choisit :

- la view à appeler ;
    
- les données à lui transmettre ;
    
- la réaction à adopter en cas d’erreur.
    

```text
HomeHandler
├── prépare les données
├── appelle RenderHome
└── gère l'erreur éventuelle
```

Le handler ne construit pas lui-même le document HTML.

Cette responsabilité reste dans la view et le template.

---

## Le handler connaît l’intention de la page

Cette ligne :

```go
data := views.HomeData{
```

signifie :

> Je prépare les informations nécessaires à la page d’accueil.

Puis :

```go
err := views.RenderHome(w, data)
```

signifie :

> Je demande à la view de produire la page d’accueil avec ces informations.

---

# 3. Transmettre les données à la view

La fonction `RenderHome` doit maintenant accepter deux paramètres :

```go
func RenderHome(
	w io.Writer,
	data HomeData,
) error {
```

Le premier paramètre :

```go
w io.Writer
```

représente la destination dans laquelle le HTML sera écrit.

Le second :

```go
data HomeData
```

représente les informations à afficher.

La fonction complète devient :

```go
func RenderHome(
	w io.Writer,
	data HomeData,
) error {
	return homeTemplate.ExecuteTemplate(
		w,
		"001_home.html",
		data,
	)
}
```

---

## Modification de l’appel

Avant :

```go
views.RenderHome(w)
```

Après :

```go
views.RenderHome(w, data)
```

La fonction a besoin d’une information supplémentaire.

```text
Avant
RenderHome(destination)

Après
RenderHome(destination, données)
```

---

# 4. Fournir les données à `ExecuteTemplate`

La méthode est appelée ainsi :

```go
homeTemplate.ExecuteTemplate(
	w,
	"001_home.html",
	data,
)
```

Elle reçoit trois arguments.

## Premier argument : la destination

```go
w
```

Le HTML produit sera écrit dans cette destination.

Dans notre handler, `w` est un :

```go
http.ResponseWriter
```

Comme `http.ResponseWriter` respecte l’interface `io.Writer`, il peut être utilisé directement.

---

## Deuxième argument : le template à exécuter

```go
"001_home.html"
```

Il indique explicitement quel template doit être exécuté.

```text
homeTemplate
      ↓
Choisir 001_home.html
```

---

## Troisième argument : les données

```go
data
```

Il s’agit de la valeur rendue accessible au template.

Avant :

```go
nil
```

Après :

```go
data
```

Le changement essentiel est donc :

```text
ExecuteTemplate(..., nil)
          ↓
ExecuteTemplate(..., data)
```

---

# 5. Utiliser les données dans le template

Le template reçoit la valeur `HomeData`.

Il peut accéder à ses champs avec la syntaxe :

```html
{{ .NomDuChamp }}
```

Pour notre structure :

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

le template peut utiliser :

```html
{{ .Title }}
{{ .Heading }}
{{ .Description }}
```

---

## Exemple complet

```html
<!DOCTYPE html>
<html lang="fr">
<head>
    <meta charset="UTF-8">

    <meta
        name="viewport"
        content="width=device-width, initial-scale=1.0"
    >

    <title>{{ .Title }}</title>
</head>

<body>
    <h1>{{ .Heading }}</h1>

    <p>{{ .Description }}</p>
</body>
</html>
```

Lors de l’exécution, Go remplace les expressions du template.

```text
{{ .Title }}
      ↓
"Club Manager"
```

```text
{{ .Heading }}
      ↓
"Bienvenue sur Club Manager"
```

```text
{{ .Description }}
      ↓
"Une application destinée à faciliter la gestion d'une association."
```

Le navigateur reçoit alors du HTML classique :

```html
<title>Club Manager</title>

<h1>Bienvenue sur Club Manager</h1>

<p>
    Une application destinée à faciliter la gestion d'une association.
</p>
```

Les expressions `{{ ... }}` n’apparaissent plus dans la réponse finale.

---

# Que représente le point `.` ?

Dans :

```html
{{ .Title }}
```

le point :

```text
.
```

représente la donnée actuellement transmise au template.

Dans notre cas :

```go
homeTemplate.ExecuteTemplate(
	w,
	"001_home.html",
	data,
)
```

la donnée courante est :

```go
data
```

Le template interprète donc :

```text
.Title
```

comme :

```text
data.Title
```

De la même manière :

```text
.Heading
```

correspond à :

```text
data.Heading
```

et :

```text
.Description
```

correspond à :

```text
data.Description
```

---

## Représentation simplifiée

```text
data
└── HomeData
    ├── Title
    ├── Heading
    └── Description
```

Dans le template :

```text
.              → data
.Title         → data.Title
.Heading       → data.Heading
.Description   → data.Description
```

---

# Pourquoi les champs commencent-ils par une majuscule ?

La structure utilise :

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

et non :

```go
type HomeData struct {
	title       string
	heading     string
	description string
}
```

En Go, un nom qui commence par une majuscule est exporté.

```text
Title
Heading
Description
```

peuvent être lus depuis le moteur de templates.

Des champs non exportés ne peuvent pas être utilisés normalement par le template.

Nous devons donc écrire :

```html
{{ .Title }}
```

avec un champ exporté :

```go
Title string
```

---

# Le template modifie-t-il les données ?

Non.

Le template reçoit les données afin de produire du HTML.

```text
HomeData
   ↓
Lecture par le template
   ↓
Production du HTML
```

Il ne modifie pas la structure originale.

Son rôle est principalement de présenter les informations reçues.

---

# Séparation des responsabilités

Après cette évolution, les responsabilités sont réparties ainsi.

## Handler

```go
func HomeHandler(
	w http.ResponseWriter,
	r *http.Request,
)
```

Responsabilités :

- recevoir la requête ;
    
- préparer les données ;
    
- appeler la view ;
    
- gérer l’erreur HTTP.
    

---

## Structure `HomeData`

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

Responsabilité :

- décrire les informations nécessaires à la page.
    

Elle forme un contrat entre le code Go et le template.

```text
La view attend une valeur HomeData.
```

---

## View

```go
func RenderHome(
	w io.Writer,
	data HomeData,
) error
```

Responsabilités :

- recevoir les données ;
    
- choisir le template ;
    
- exécuter le template ;
    
- écrire le HTML produit.
    

---

## Template

```html
<title>{{ .Title }}</title>
<h1>{{ .Heading }}</h1>
<p>{{ .Description }}</p>
```

Responsabilités :

- décrire la structure HTML ;
    
- choisir où afficher chaque donnée.
    

---

# La structure comme contrat

La structure `HomeData` établit un lien entre le code et le template.

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

Le code Go promet de fournir ces informations.

Le template indique comment les afficher :

```html
{{ .Title }}
{{ .Heading }}
{{ .Description }}
```

Nous pouvons représenter ce contrat ainsi :

```text
HomeData.Title
      ↕
{{ .Title }}

HomeData.Heading
      ↕
{{ .Heading }}

HomeData.Description
      ↕
{{ .Description }}
```

Si nous renommons un champ Go, nous devons également adapter le template.

Par exemple :

```go
Heading string
```

devient :

```go
MainTitle string
```

Le template doit alors utiliser :

```html
{{ .MainTitle }}
```

et non plus :

```html
{{ .Heading }}
```

---

# Parcours complet d’une donnée

Prenons le titre principal :

```go
Heading: "Bienvenue sur Club Manager",
```

## Étape 1 : création dans le handler

```go
data := views.HomeData{
	Heading: "Bienvenue sur Club Manager",
}
```

## Étape 2 : transmission à la view

```go
views.RenderHome(w, data)
```

## Étape 3 : transmission au template

```go
homeTemplate.ExecuteTemplate(
	w,
	"001_home.html",
	data,
)
```

## Étape 4 : lecture par le template

```html
<h1>{{ .Heading }}</h1>
```

## Étape 5 : production du HTML

```html
<h1>Bienvenue sur Club Manager</h1>
```

Le parcours complet est donc :

```text
"Bienvenue sur Club Manager"
            ↓
data.Heading
            ↓
RenderHome(w, data)
            ↓
ExecuteTemplate(..., data)
            ↓
{{ .Heading }}
            ↓
<h1>Bienvenue sur Club Manager</h1>
```

---

# Où les données pourront-elles venir plus tard ?

Pour le moment, les valeurs sont directement écrites dans le handler :

```go
data := views.HomeData{
	Title: "Club Manager",
}
```

Plus tard, elles pourront provenir :

- d’un fichier de configuration ;
    
- d’un service ;
    
- d’une base de données ;
    
- de paramètres présents dans l’URL ;
    
- d’un formulaire ;
    
- de l’utilisateur connecté.
    

Le parcours pourra devenir :

```text
Base de données
      ↓
Service
      ↓
Handler
      ↓
HomeData
      ↓
View
      ↓
Template
```

Le template n’aura pas besoin de connaître la provenance des données.

Il recevra toujours une structure contenant les informations à afficher.

---

# Pourquoi ne pas interroger la base de données depuis le template ?

Le template doit rester centré sur la présentation.

Il ne doit pas :

- ouvrir une connexion à la base ;
    
- exécuter une requête SQL ;
    
- décider des règles métier ;
    
- rechercher lui-même les informations.
    

Le bon parcours sera :

```text
Le code Go récupère les informations
               ↓
Le handler prépare les données de la page
               ↓
Le template affiche ces données
```

Cela conserve une séparation claire des responsabilités.

---

# Tester le passage des données

Les tests existants recherchent déjà un contenu dans la réponse.

Par exemple :

```go
testHandler(
	t,
	"/",
	"Bienvenue",
	HomeHandler,
)
```

Même si le texte vient maintenant d’une structure Go, le résultat final reste du HTML.

Le test vérifie donc toujours le comportement observable :

```text
La réponse contient-elle "Bienvenue" ?
```

Nous ne testons pas uniquement l’emplacement où le texte est écrit dans le code.

Nous testons le résultat produit par toute la chaîne :

```text
Handler
   ↓
Données
   ↓
View
   ↓
Template
   ↓
Réponse HTTP
```

# Erreurs fréquentes

## Oublier de transmettre les données

```go
homeTemplate.ExecuteTemplate(
	w,
	"001_home.html",
	nil,
)
```

Le template ne reçoit alors pas la valeur `HomeData`.

Les expressions comme :

```html
{{ .Title }}
```

ne peuvent pas afficher la valeur attendue.

---

## Utiliser un mauvais nom de champ

Structure :

```go
type HomeData struct {
	Heading string
}
```

Template incorrect :

```html
{{ .Header }}
```

Template correct :

```html
{{ .Heading }}
```

Le nom doit correspondre exactement au champ exporté.

---

## Utiliser un champ non exporté

```go
type HomeData struct {
	title string
}
```

Le template ne peut pas utiliser correctement :

```html
{{ .title }}
```

Il faut écrire :

```go
type HomeData struct {
	Title string
}
```

puis :

```html
{{ .Title }}
```

---

## Oublier le nouvel argument de `RenderHome`

Après avoir changé la signature :

```go
func RenderHome(
	w io.Writer,
	data HomeData,
) error
```

cet appel n’est plus suffisant :

```go
views.RenderHome(w)
```

Il faut transmettre les données :

```go
views.RenderHome(w, data)
```

    ├── 001_home.go
    │
    └── templates/

views/001_home.go

views/templates/001_home.html

# Comprendre et retenir

Une structure regroupe les données nécessaires à une page :

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

Le handler construit cette structure :

```go
data := views.HomeData{
	Title:       "Club Manager",
	Heading:     "Bienvenue sur Club Manager",
	Description: "Une application destinée à faciliter la gestion d'une association.",
}
```

Il la transmet à la view :

```go
views.RenderHome(w, data)
```

La view la transmet au template :

```go
homeTemplate.ExecuteTemplate(
	w,
	"001_home.html",
	data,
)
```

Le template accède aux champs avec le point :

```html
{{ .Title }}
{{ .Heading }}
{{ .Description }}
```

Le point représente la donnée reçue :

```text
.              → data
.Title         → data.Title
.Heading       → data.Heading
.Description   → data.Description
```

Le parcours complet est :

```text
Handler
   ↓
HomeData
   ↓
RenderHome
   ↓
ExecuteTemplate
   ↓
{{ .Champ }}
   ↓
HTML final
```

La règle essentielle à retenir est :

> Le code Go prépare les données, la view les transmet et le template décide comment les afficher.

Remarque : 

Pourquoi la struct 

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

est dans la view et non le handler ?

La question principale n’est pas :

> Qui remplit la structure ?

Mais plutôt :

> À quelle responsabilité cette structure appartient-elle ?

Ici :

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

décrit précisément ce dont le template `001_home.html` a besoin.

Elle constitue donc le **contrat de la vue** :

```
La vue demande :
- un Title
- un Heading
- une Description
```

Le handler construit ce contrat, mais il n’en est pas nécessairement le propriétaire.

## Le rôle du handler

Le handler coordonne le traitement :

```go
func HomeHandler(w http.ResponseWriter, r *http.Request) {
	data := views.HomeData{
		Title:       "Club Manager",
		Heading:     "Bienvenue sur Club Manager",
		Description: "Une application destinée à faciliter la gestion d'une association.",
	}

	err := views.RenderHome(w, data)
	// Gestion de l'erreur...
}
```

Il fait essentiellement ceci :

```
1. recevoir la requête ;
2. récupérer ou préparer les informations ;
3. construire les données attendues par la vue ;
4. appeler la vue ;
5. gérer l'erreur HTTP.
```

Le handler **utilise** `HomeData`, mais la structure décrit avant tout les besoins du rendu HTML.

## Pourquoi ne pas la placer dans `handlers` ?

Nous pourrions techniquement écrire :

```go
package handlers

type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

Mais `RenderHome` aurait alors besoin de recevoir ce type :

```go
func RenderHome(w io.Writer, data handlers.HomeData) error
```

Le package `views` devrait donc importer `handlers`.

Or, actuellement, le handler importe déjà la vue :

```
handlers
    ↓ importe
views
```

Si `views` importait également `handlers`, nous aurions :

```
handlers
    ↓
views
    ↓
handlers
```

Cela créerait une **dépendance circulaire**, interdite en Go.

```
handlers → views → handlers
```

Go refuserait de compiler le programme.

## Sens de dépendance actuel

L’organisation actuelle est simple :

```
handlers
    ↓ utilise
views.HomeData
    ↓ utilise
template HTML
```

La vue ne connaît pas le handler.

```
handler connaît la view
view ne connaît pas le handler
```

C’est généralement préférable.

## Une distinction importante

Dire que le handler « gère les données » peut prêter à confusion.

Il serait plus précis de dire :

> Le handler récupère, prépare et transmet les données nécessaires à la réponse HTTP.

Il ne possède pas nécessairement tous les types de données utilisés par l’application.

Par exemple :

```go
Member
```

pourrait appartenir au domaine métier.

```go
HomeData
```

appartient à la présentation de la page d’accueil.

Ce sont deux types de structures différents.

### Structure métier

```go
type Member struct {
	ID        int
	FirstName string
	LastName  string
}
```

Elle représente une notion réelle de l’application :

```
un membre du club
```

Elle ne devrait probablement pas être placée dans `views`.

### Structure de présentation

```go
type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

Elle représente ce que la page doit afficher :

```
les données nécessaires au template d'accueil
```

Elle trouve naturellement sa place dans `views`.

## Plus tard : un package dédié

Si les données de présentation deviennent nombreuses, nous pourrions créer un package spécifique :

```
internal/
├── handlers/
├── views/
└── viewmodels/
```

Avec :

```
package viewmodels

type HomeData struct {
	Title       string
	Heading     string
	Description string
}
```

Le handler et la vue pourraient alors importer ce package :

```
          viewmodels
          ↑        ↑
    handlers      views
```

Mais pour Club Manager aujourd’hui, cela ajouterait une couche sans réel bénéfice.

## Règle pratique

Tu peux retenir cette question :

> Cette structure représente-t-elle une notion métier ou les besoins d’une page ?

Si elle représente une notion métier :

```
Member
Membership
Payment
Schedule
```

elle appartient plutôt au modèle ou au domaine.

Si elle représente les données nécessaires à un template :

```
HomeData
ContactPageData
MemberListData
```

elle appartient plutôt à la couche de présentation, donc ici à `views`.

## Conclusion

Dans notre architecture :

```
HomeData
```

est placée dans `views` parce qu’elle décrit le contrat attendu par `RenderHome` et `001_home.html`.

Le handler ne possède pas la structure : il la construit et la transmet.

```
views définit ce dont la page a besoin
              ↓
handler fournit ces informations
              ↓
template les affiche
```

Ton raisonnement reste néanmoins pertinent : le handler manipule bien les données. La nuance est qu’il **orchestre leur passage**, tandis que la vue **définit leur forme pour l’affichage**.
