# Charger et tester une configuration JSON en Go

## Objectif

Dans Club Manager, nous voulons déplacer certains paramètres généraux en dehors du code source.

La première configuration utilisée est très simple :

```json
{
  "site_name": "Club Manager"
}
```

L’objectif est de transformer cette donnée JSON en une structure Go utilisable par l’application.

Le parcours général est :

```text
Fichier JSON
    ↓
Ouverture du fichier
    ↓
Décodage du JSON
    ↓
Structure Config
    ↓
Données utilisables par Go
```

Pour le moment, la configuration est uniquement chargée et testée.

Elle n’est pas encore transmise à `main.go`, au routeur ou aux handlers.

# 3. La structure `Config`

Le fichier `config.go` contient la structure suivante :

```go
type Config struct {
	SiteName string `json:"site_name"`
}
```

Cette structure représente la configuration dans le programme Go.

La correspondance est :

```text
JSON                    Go

"site_name"    →        SiteName
"Club Manager" →        valeur du champ
```

Après le chargement, nous pourrons utiliser :

```go
cfg.SiteName
```

La valeur obtenue sera :

```text
Club Manager
```

---

## Pourquoi utiliser une structure ?

Il serait possible de représenter le JSON avec une `map`.

Par exemple :

```go
map[string]string
```

Cependant, une structure est mieux adaptée lorsque les propriétés attendues sont connues à l’avance.

```go
type Config struct {
	SiteName string
}
```

La structure permet de connaître clairement :

- le nom du champ ;
    
- son type ;
    
- les données attendues ;
    
- les propriétés disponibles dans la configuration.
    

```text
Config
└── SiteName
    └── string
```

Elle apporte davantage de précision qu’une collection générique de clés et de valeurs.

---

## Pourquoi `SiteName` commence-t-il par une majuscule ?

En Go, un nom commençant par une majuscule est exporté :

```go
SiteName
```

Le package `encoding/json` doit pouvoir accéder au champ pour lui attribuer une valeur.

Cette version peut être remplie par le décodeur :

```go
type Config struct {
	SiteName string
}
```

Cette version ne peut pas être remplie directement par `encoding/json` :

```go
type Config struct {
	siteName string
}
```

Le champ `siteName` n’est pas exporté.

---

# 4. L’annotation JSON

Le champ possède une annotation :

```go
SiteName string `json:"site_name"`
```

La partie suivante :

```go
`json:"site_name"`
```

est appelée un tag de structure.

Elle indique au package `encoding/json` :

> La propriété JSON nommée `site_name` correspond au champ Go `SiteName`.

La correspondance est donc explicite :

```text
site_name
    ↓
SiteName
```

Cela permet également d’utiliser deux conventions différentes :

```text
JSON
└── snake_case
    └── site_name

Go
└── PascalCase
    └── SiteName
```

# 5. La fonction `Load`

Le package expose une fonction chargée de lire la configuration :

```go
func Load(path string) (Config, error)
```

Cette signature indique que la fonction reçoit :

```text
path string
└── chemin du fichier à charger
```

et retourne :

```text
Config
└── configuration obtenue

error
└── éventuelle erreur
```

L’utilisation future pourra ressembler à ceci :

```go
cfg, err := config.Load("config/config.json")
```

---

# Implémentation complète

```go
package config

import (
	"encoding/json"
	"fmt"
	"os"
)

// Config contient les paramètres généraux
// chargés au démarrage de l'application.
type Config struct {
	SiteName string `json:"site_name"`
}

// Load ouvre le fichier situé au chemin reçu,
// décode son contenu JSON et retourne la configuration.
//
// Une erreur est retournée si le fichier ne peut pas être
// ouvert ou si son contenu n'est pas un JSON valide.
func Load(path string) (Config, error) {
	file, err := os.Open(path)
	if err != nil {
		return Config{}, fmt.Errorf(
			"ouvrir le fichier de configuration : %w",
			err,
		)
	}
	defer file.Close()

	var cfg Config

	err = json.NewDecoder(file).Decode(&cfg)
	if err != nil {
		return Config{}, fmt.Errorf(
			"décoder le fichier de configuration : %w",
			err,
		)
	}

	return cfg, nil
}
```

# 6. Ouvrir le fichier

La première étape consiste à ouvrir le fichier reçu :

```go
file, err := os.Open(path)
```

Si `path` vaut :

```text
config/config.json
```

Go essaie d’ouvrir ce fichier.

`os.Open` retourne deux éléments :

```text
file
└── accès au contenu du fichier

err
└── erreur éventuelle
```

Une erreur peut être retournée si :

- le fichier n’existe pas ;
    
- le chemin est incorrect ;
    
- les permissions sont insuffisantes ;
    
- le chemin correspond à un dossier ;
    
- le fichier n’est pas accessible.
    

---

## Traiter immédiatement l’erreur

Après l’ouverture :

```go
if err != nil {
	return Config{}, fmt.Errorf(
		"ouvrir le fichier de configuration : %w",
		err,
	)
}
```

Si le fichier ne peut pas être ouvert, il est inutile de poursuivre.

La fonction retourne donc :

```text
Config{}
└── configuration vide

error
└── description du problème
```

La structure vide équivaut ici à :

```go
Config{
	SiteName: "",
}
```

---

# 7. Fermer le fichier avec `defer`

Une fois le fichier ouvert, il devra être fermé :

```go
defer file.Close()
```

`defer` signifie :

> Exécuter cette instruction juste avant de quitter la fonction.

Le parcours devient :

```text
os.Open
    ↓
fichier ouvert
    ↓
defer prépare file.Close()
    ↓
décodage du JSON
    ↓
retour de la fonction
    ↓
fermeture du fichier
```

La fermeture est nécessaire, car un fichier ouvert utilise une ressource du système d’exploitation.

L’utilisation de `defer` permet de placer la fermeture juste après l’ouverture réussie.

Cela rend le code plus facile à lire :

```go
file, err := os.Open(path)
if err != nil {
	// gestion de l'erreur
}

defer file.Close()
```

# 8. Créer une configuration vide

Avant de décoder le JSON, nous déclarons :

```go
var cfg Config
```

Cette déclaration crée une structure contenant les valeurs par défaut de ses champs.

Pour une chaîne de caractères, la valeur par défaut est une chaîne vide :

```go
Config{
	SiteName: "",
}
```

Le décodeur JSON remplira ensuite cette structure.

---

# 9. Décoder le fichier JSON

Le décodage est réalisé avec :

```go
err = json.NewDecoder(file).Decode(&cfg)
```

Cette instruction peut être décomposée en deux parties.

---

## Créer un décodeur

```go
json.NewDecoder(file)
```

Le décodeur reçoit le fichier comme source de données.

```text
file
    ↓
json.Decoder
```

Il lira progressivement son contenu JSON.

---

## Décoder dans la structure

```go
Decode(&cfg)
```

Le décodeur transforme les données JSON et remplit `cfg`.

Avant le décodage :

```go
cfg.SiteName == ""
```

Après le décodage :

```go
cfg.SiteName == "Club Manager"
```

---

# 10. Pourquoi utiliser `&cfg` ?

Nous transmettons :

```go
&cfg
```

et non simplement :

```go
cfg
```

Le symbole `&` permet d’obtenir l’adresse de la variable.

Le décodeur doit pouvoir modifier la structure originale.

```text
cfg
└── structure originale

&cfg
└── adresse permettant de modifier cette structure
```

Sans pointeur, le décodeur ne pourrait pas remplir directement notre variable.

Le parcours est :

```text
JSON
    ↓
Decode(&cfg)
    ↓
modification de cfg
    ↓
cfg.SiteName = "Club Manager"
```

---

# 11. Retourner la configuration

Lorsque le décodage réussit :

```go
return cfg, nil
```

La fonction retourne :

```text
cfg
└── configuration remplie

nil
└── aucune erreur
```

L’appelant pourra donc écrire :

```go
cfg, err := Load("config/config.json")
```

puis utiliser :

```go
cfg.SiteName
```

---

# 12. Ajouter du contexte aux erreurs

La fonction utilise :

```go
fmt.Errorf(
	"ouvrir le fichier de configuration : %w",
	err,
)
```

et :

```go
fmt.Errorf(
	"décoder le fichier de configuration : %w",
	err,
)
```

L’objectif est de rendre les erreurs plus compréhensibles.

Une erreur brute pourrait être :

```text
no such file or directory
```

Avec du contexte :

```text
ouvrir le fichier de configuration :
no such file or directory
```

Nous savons maintenant pendant quelle étape l’erreur s’est produite.

---

## Le rôle de `%w`

Le format `%w` permet d’envelopper une erreur.

```go
fmt.Errorf("contexte : %w", err)
```

Il ajoute une explication tout en conservant l’erreur originale.

```text
nouvelle erreur
├── contexte ajouté par notre application
└── erreur originale
```

À ce stade, il faut surtout retenir :

```text
%w
└── ajoute du contexte sans perdre l’erreur d’origine
```

# 13. Pourquoi tester avec un fichier séparé ?

Le véritable fichier de configuration est :

```text
config/config.json
```

Les tests pourraient techniquement utiliser ce fichier.

Cependant, ce serait une mauvaise dépendance.

Le contenu de la véritable configuration pourra évoluer :

```json

  "site_name": "Club Manager"
}
```

pourrait devenir :

```json

  "site_name": "Budokan Sud Oise"

```

Le test ne doit pas échouer simplement parce que la configuration réelle a été personnalisée.

Nous utilisons donc un fichier réservé aux tests :


# 16. Tester un chargement réussi

Le premier test vérifie que la configuration valide peut être chargée.

```go
func TestLoad(t *testing.T) {
	cfg, err := Load("testdata/config.json")
	if err != nil {
		t.Fatalf(
			"le chargement de la configuration a échoué : %v",
			err,
		)
	}

	expectedSiteName := "Club Manager"

	if cfg.SiteName != expectedSiteName {
		t.Errorf(
			"nom du site obtenu : %q, nom attendu : %q",
			cfg.SiteName,
			expectedSiteName,
		)
	}
}
```

Le parcours du test est :

```text
Fichier testdata/config.json
        ↓
Load
        ↓
Config
        ↓
lecture de cfg.SiteName
        ↓
comparaison avec la valeur attendue
```

---

## Le résultat attendu

Le test définit :

```go
expectedSiteName := "Club Manager"
```

Il compare ensuite :

```go
cfg.SiteName
```

avec :

```go
expectedSiteName
```

La condition vérifiée est :

```text
valeur obtenue == valeur attendue
```

---

# 17. Pourquoi utiliser `t.Fatalf` ?

Le test commence par vérifier l’erreur :

```go
if err != nil {
	t.Fatalf(
		"le chargement de la configuration a échoué : %v",
		err,
	)
}
```

Si le chargement échoue, la configuration n’est pas exploitable.

Il est inutile de continuer avec :

```go
cfg.SiteName
```

`t.Fatalf` possède deux effets :

```text
1. signaler l’échec du test
2. arrêter immédiatement ce test
```

Cette décision est adaptée lorsque la suite du test dépend absolument de la réussite de l’étape précédente.

---

# 18. Pourquoi utiliser ensuite `t.Errorf` ?

Après un chargement réussi, nous comparons la valeur :

```go
if cfg.SiteName != expectedSiteName {
	t.Errorf(...)
}
```

Ici, nous voulons signaler une différence entre le résultat obtenu et le résultat attendu.

Le test pourrait techniquement continuer avec d’autres comparaisons.

```text
t.Fatalf
└── erreur empêchant la suite du test

t.Errorf
└── résultat incorrect pouvant être signalé sans arrêt immédiat
```

# 19. Tester le cas d’erreur

Nous devons également vérifier le comportement lorsque le fichier n’existe pas.

```go
func TestLoadReturnsErrorWhenFileDoesNotExist(t *testing.T) {
	_, err := Load("testdata/unknown.json")

	if err == nil {
		t.Fatal(
			"une erreur était attendue pour un fichier inexistant",
		)
	}
}
```

Le test demande volontairement le chargement d’un fichier absent :

```text
testdata/unknown.json
```

Le comportement attendu est :

```text
fichier inexistant
        ↓
Load
        ↓
erreur non nulle
```

---

## Pourquoi ignorer la configuration retournée ?

L’appel utilise :

```go
_, err := Load("testdata/unknown.json")
```

Le symbole `_` est l’identificateur vide de Go.

Il permet d’ignorer une valeur qui ne nous intéresse pas.

Dans ce test :

```text
Config retournée
└── ignorée

error retournée
└── vérifiée
```

Nous testons uniquement que l’erreur existe.

---

# 20. Tester les comportements, pas l’implémentation

Les tests ne cherchent pas à vérifier que :

- `os.Open` fonctionne ;
    
- `json.NewDecoder` fonctionne ;
    
- `Decode` fonctionne ;
    
- `defer` fonctionne.
    

Ces éléments appartiennent à la bibliothèque standard de Go.

Nous testons les comportements de notre fonction :

```text
Fichier valide
└── retourne une configuration correcte

Fichier inexistant
└── retourne une erreur
```

Cela permet de modifier plus tard l’implémentation interne tout en conservant les mêmes tests.

Par exemple, `Load` pourrait un jour utiliser :

```go
os.ReadFile
```

au lieu de :

```go
os.Open
```

Les comportements attendus resteraient identiques.

# 21. Pourquoi ne pas utiliser la véritable configuration dans le test ?

Un test doit être :

- prévisible ;
    
- reproductible ;
    
- indépendant ;
    
- stable ;
    
- contrôlé.
    

Si le test utilisait :

```text
config/config.json
```

son résultat dépendrait d’un fichier destiné à l’application réelle.

Un utilisateur pourrait modifier :

```json
{
  "site_name": "Club Manager"
}
```

en :

```json
{
  "site_name": "Mon association"
}
```

Le test échouerait alors, même si la fonction `Load` fonctionne parfaitement.

Avec `testdata` :

```text
le test contrôle ses propres données
```

Cela évite de confondre :

```text
modification légitime de configuration
```

avec :

```text
régression dans le code
```

```text
  ↓

  ↓

  ↓
```


```
internal/config/testdata/config.json
```

## Pourquoi ne pas tester avec le vrai fichier ?

Le test vérifie actuellement :

```go
cfg, err := Load("testdata/config.json")
```

Il doit pouvoir affirmer avec certitude que le fichier contient :

```JSON
{
  "site_name": "Club Manager"
}
```

Supposons que la configuration réelle soit ensuite personnalisée :

```JSON
{
  "site_name": "Budokan Sud Oise"
}
```

Si le test utilisait `config/config.json`, il échouerait parce qu’il attend encore `"Club Manager"` — alors que la fonction `Load` fonctionnerait parfaitement.

Le test serait donc dépendant d’une donnée extérieure à ce qu’il contrôle.

Avec son propre fichier :

```
testdata/config.json
```

le test maîtrise son environnement :

```
entrée connue
    ↓
Load
    ↓
résultat attendu connu
```

## Les fichiers pourront diverger

Aujourd’hui :

```
config/config.json
└── Club Manager

testdata/config.json
└── Club Manager
```

Plus tard :

```
config/config.json
└── Budokan Sud Oise

testdata/config.json
└── Club Manager
```

Et les tests continueront à fonctionner normalement.

## Ce n’est pas vraiment une duplication applicative

L’application réelle ne lit qu’un seul fichier :

```
config/config.json
```

Le fichier placé dans `testdata` n’est jamais utilisé par le serveur. C’est une **fixture de test**, c’est-à-dire une donnée préparée spécialement pour vérifier un comportement.

```
En production
└── config/config.json

Pendant go test
└── internal/config/testdata/config.json
```

## Pourrait-on éviter le second fichier ?

Oui. Le test pourrait créer temporairement son propre fichier avec `os.CreateTemp`, y écrire du JSON, exécuter `Load`, puis supprimer le fichier.

Mais cela ajouterait plusieurs notions :

- création de fichiers temporaires ;
- écriture dans un fichier ;
- fermeture ;
- suppression ;
- gestion d’erreurs supplémentaires.

Pour notre progression actuelle, `testdata/config.json` est plus simple et plus lisible. En ouvrant le dossier, on voit immédiatement l’entrée utilisée par le test.

## À retenir

Les deux fichiers représentent deux environnements différents :

```
configuration réelle
≠
configuration de test
```

Même lorsqu’ils ont temporairement le même contenu, les séparer garantit que les tests restent :

- prévisibles ;
- indépendants ;
- reproductibles ;
- insensibles à la personnalisation de l’application.

C’est donc une petite duplication volontaire, au service de la fiabilité des tests.
