## À quoi sert la clé SSH générée ?

Quand tu as exécuté :

```
ssh-keygen -t ed25519 -C "remigrapinou@gmail.com"
```

tu as créé une **paire de clés cryptographiques** :

```
              Clé SSH

        ┌────────────────┐
        │                │
        │  Clé privée    │  🔒
        │ id_ed25519     │
        │                │
        └────────────────┘
                +
        ┌────────────────┐
        │                │
        │  Clé publique  │  🔑
        │ id_ed25519.pub │
        │                │
        └────────────────┘
```

Les deux clés fonctionnent ensemble.

---

# Une analogie simple : une serrure et une clé

Imagine une porte :

- La **clé publique** est comme la serrure installée sur la porte.
- La **clé privée** est comme ta clé physique pour ouvrir cette porte.

Tu donnes la serrure à GitHub.

Tu gardes la clé chez toi.

GitHub peut alors vérifier :

> "La personne qui se présente possède-t-elle bien la clé privée correspondante ?"

Sans jamais recevoir ta clé privée.

Avant :

```
Ton PC

 |

```

Mais GitHub a supprimé l'authentification par mot de passe.

Maintenant :

```

    |
    | preuve cryptographique
    |
    ▼

GitHub

id_ed25519.pub 🔑
```

GitHub possède seulement la clé publique.

# Concrètement, lors d'un `git push`

Quand tu fais :

```
git push
```

Il se passe quelque chose comme :

1. Ton ordinateur dit :
    
    > "Bonjour GitHub, je possède une clé."
    
2. GitHub répond :
    
    > "Prouve-le."
    
3. Ton ordinateur utilise la clé privée pour signer une preuve.
4. GitHub vérifie avec la clé publique.
5. Si ça correspond :
    
    > "OK, tu es bien Rémi, tu peux envoyer le code."

# Pourquoi deux fichiers ?

Dans ton dossier :

```
~/.ssh/

-rw------- id_ed25519
-rw-r--r-- id_ed25519.pub
```

## `id_ed25519`

C'est la clé privée.

Règle absolue :

❌ Ne jamais :

- l'envoyer par mail ;
- la mettre sur GitHub ;
- la copier sur un forum ;
- la partager.

Si quelqu'un l'obtient **et connaît ton ordinateur GitHub associé**, il pourrait se faire passer pour toi.

---

## `id_ed25519.pub`

C'est la clé publique.

C'est celle que tu as donnée à GitHub.

Elle peut être connue publiquement.

Elle ressemble à :

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... remigrapinou@gmail.com
```

Ce n'est pas un secret.

---

# Pourquoi Ed25519 ?

Tu as utilisé :

```
ssh-keygen -t ed25519
```

Ed25519 est aujourd'hui un excellent choix :

- 🔒 très sécurisé ;
- ⚡ rapide ;
- 🔑 clé courte ;
- moins sujet aux erreurs que les anciennes clés RSA.

Avant, on utilisait souvent :

```
ssh-keygen -t rsa -b 4096
```

Mais aujourd'hui Ed25519 est généralement préféré.

---

# Et le fichier `authorized_keys` que tu avais déjà ?

Très bonne observation.

Tu avais :

```
~/.ssh/authorized_keys
```

Vide.

Ce fichier sert à autre chose.

Il sert quand **une machine extérieure veut se connecter à ton ordinateur**.

Exemple :

```
Serveur distant
       |
       | SSH
       |
       ▼
Ton PC Ubuntu

authorized_keys
```

Il contient les clés publiques des personnes autorisées à se connecter.

Pour GitHub, c'est l'inverse :

```
Ton PC
       |
       |
       ▼
GitHub
```

# Pour ta future fiche Obsidian, je noterais :

```
# Authentification SSH

## Principe

SSH utilise une paire de clés cryptographiques :

- clé privée : reste sur la machine, ne jamais partager.
- clé publique : peut être transmise aux services (GitHub, serveurs...).

## Création

ssh-keygen -t ed25519 -C "email"

## Fichiers générés

~/.ssh/id_ed25519
→ clé privée

~/.ssh/id_ed25519.pub
→ clé publique

## Fonctionnement

La clé privée prouve mon identité.
La clé publique permet au serveur de vérifier cette identité.

## GitHub

La clé publique est ajoutée dans :
Settings → SSH and GPG keys

Puis Git utilise :

git@github.com:utilisateur/projet.git
```
