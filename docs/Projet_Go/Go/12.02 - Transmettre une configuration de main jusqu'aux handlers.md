MOC : [[12 - FICHIER DE CONFIGURATION ET JSON]]

---


## Objectif

L’application charge maintenant un fichier de configuration au démarrage.

Nous voulons transmettre cette configuration jusqu’aux handlers afin qu’ils puissent utiliser les données du fichier JSON.

La circulation de la configuration devient :

```text
config/config.json
        ↓
config.Load()
        ↓
main
        ↓
router.New(cfg)
        ↓
HomeHandler(cfg)
ClubHandler(cfg)
        ↓
views
        ↓
templates HTML
```

Cette progression permet de remplacer certaines valeurs écrites directement dans le code par des données provenant de la configuration.

---

# Configuration utilisée

Le fichier JSON contient pour l’instant :

```json
{
  "site_name": "Club Manager"
}
```

La structure Go correspondante est :

```go
type Config struct {
	SiteName string `json:"site_name"`
}
```

Après le chargement, la valeur est accessible avec :

```go
cfg.SiteName
```

---

# 1. Charger la configuration dans `main`

Le programme principal connaît le chemin du fichier de configuration :

```go
const configPath = "config/config.json"
```

La configuration est chargée au démarrage :

```go
cfg, err := config.Load(configPath)
if err != nil {
	log.Fatalf(
		"impossible de charger la configuration depuis %q : %v",
		configPath,
		err,
	)
}
```

Si le fichier ne peut pas être chargé, l’application ne peut pas démarrer correctement.

L’erreur est donc considérée comme fatale.

---

## Rôle de `main`

`main` est responsable de la création des principales dépendances de l’application.

Dans notre cas :

```text
main
├── charge Config
├── construit le routeur
└── démarre le serveur HTTP
```

Le routeur est ensuite construit avec la configuration :

```go
mux := router.New(cfg)
```

Le `main` complet ressemble à :

```go
package main

import (
	"log"
	"net/http"

	"github.com/grapinou/club-manager/internal/config"
	"github.com/grapinou/club-manager/internal/router"
)

const configPath = "config/config.json"

func main() {
	cfg, err := config.Load(configPath)
	if err != nil {
		log.Fatalf(
			"impossible de charger la configuration depuis %q : %v",
			configPath,
			err,
		)
	}

	mux := router.New(cfg)

	log.Println("Serveur lancé sur http://localhost:8080")

	if err := http.ListenAndServe(":8080", mux); err != nil {
		log.Fatal(err)
	}
}
```

---

# 2. Transmettre la configuration au routeur

Avant l’introduction de la configuration, le routeur était créé sans argument :

```go
func New() *http.ServeMux
```

Il est maintenant créé avec une configuration :

```go
func New(cfg config.Config) *http.ServeMux
```

Le routeur devient :

```go
package router

import (
	"net/http"

	"github.com/grapinou/club-manager/internal/config"
	"github.com/grapinou/club-manager/internal/handlers"
)

func New(cfg config.Config) *http.ServeMux {
	mux := http.NewServeMux()

	mux.HandleFunc("GET /{$}", handlers.HomeHandler(cfg))
	mux.HandleFunc("GET /club", handlers.ClubHandler(cfg))
	mux.HandleFunc("GET /contact", handlers.ContactHandler)
	mux.HandleFunc("GET /rules", handlers.RulesHandler)

	return mux
}
```

---

## Rôle du routeur

Le routeur ne charge pas lui-même le fichier JSON.

Il reçoit une configuration déjà construite :

```go
func New(cfg config.Config)
```

Il la transmet ensuite aux handlers qui en ont besoin :

```go
handlers.HomeHandler(cfg)
handlers.ClubHandler(cfg)
```

Le routeur joue ici un rôle de distribution :

```text
main
  ↓
router
  ├── HomeHandler
  ├── ClubHandler
  ├── ContactHandler
  └── RulesHandler
```

Tous les handlers ne sont pas obligés de recevoir la configuration.

Un handler qui n’en a pas besoin peut conserver sa forme habituelle :

```go
func ContactHandler(
	w http.ResponseWriter,
	r *http.Request,
)
```

---

# 3. Transformer un handler pour recevoir `Config`

Un handler HTTP classique possède cette signature :

```go
func HomeHandler(
	w http.ResponseWriter,
	r *http.Request,
)
```

Mais cette signature ne permet pas de lui transmettre directement une configuration.

Nous transformons donc `HomeHandler` en une fonction qui :

1. reçoit la configuration ;
    
2. retourne un véritable handler HTTP.
    

```go
func HomeHandler(cfg config.Config) http.HandlerFunc
```

---

## Implémentation

```go
func HomeHandler(cfg config.Config) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		data := views.HomeData{
			Title:       cfg.SiteName,
			Heading:     "Bienvenue sur " + cfg.SiteName,
			Description: "Une application destinée à faciliter la gestion d'une association.",
		}

		err := views.RenderHome(w, data)
		if err != nil {
			http.Error(
				w,
				"Erreur interne du serveur",
				http.StatusInternalServerError,
			)
		}
	}
}
```

---

## Décomposition

La fonction extérieure reçoit la configuration :

```go
func HomeHandler(cfg config.Config) http.HandlerFunc
```

Elle retourne une fonction interne :

```go
return func(w http.ResponseWriter, r *http.Request) {
	// traitement de la requête
}
```

Cette fonction interne possède exactement la signature attendue par `http.HandleFunc` :

```go
func(http.ResponseWriter, *http.Request)
```

---

## Fonction de construction

`HomeHandler` n’est donc plus directement un handler.

C’est une fonction qui construit un handler :

```text
HomeHandler
    ↓ reçoit Config
HomeHandler(cfg)
    ↓ retourne
http.HandlerFunc
```

Le routeur enregistre le résultat :

```go
mux.HandleFunc(
	"GET /{$}",
	handlers.HomeHandler(cfg),
)
```

---

# 4. La configuration reste disponible

La fonction interne utilise `cfg` :

```go
Heading: "Bienvenue sur " + cfg.SiteName,
```

Même après la fin de l’appel à :

```go
HomeHandler(cfg)
```

la fonction retournée conserve l’accès à la configuration.

Ce mécanisme est appelé une **fermeture**, ou _closure_.

```text
HomeHandler(cfg)
        ↓
création d’une fonction interne
        ↓
la fonction conserve l’accès à cfg
        ↓
le routeur enregistre cette fonction
        ↓
une requête arrive plus tard
        ↓
la fonction utilise encore cfg.SiteName
```

---

# 5. Exemple avec `ClubHandler`

Le même principe est utilisé pour la page du club :

```go
func ClubHandler(cfg config.Config) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		data := views.ClubData{
			Title:       "Le club - " + cfg.SiteName,
			Heading:     "Présentation du club",
			Description: "Découvrez l'association, son histoire et ses valeurs.",
		}

		err := views.RenderClub(w, data)
		if err != nil {
			http.Error(
				w,
				"Erreur interne du serveur",
				http.StatusInternalServerError,
			)
		}
	}
}
```

Le routeur utilise alors :

```go
mux.HandleFunc(
	"GET /club",
	handlers.ClubHandler(cfg),
)
```

---

# 6. Pourquoi ne pas charger le fichier dans le handler ?

On pourrait imaginer ceci :

```go
func HomeHandler(
	w http.ResponseWriter,
	r *http.Request,
) {
	cfg, err := config.Load("config/config.json")

	// ...
}
```

Cette approche pose plusieurs problèmes.

Le fichier serait relu à chaque requête :

```text
requête 1 → lecture du fichier
requête 2 → lecture du fichier
requête 3 → lecture du fichier
```

Le handler deviendrait également responsable de trop de choses :

```text
HomeHandler
├── connaître le chemin du fichier
├── ouvrir le fichier
├── décoder le JSON
├── gérer les erreurs de configuration
├── construire les données de vue
└── produire la réponse HTTP
```

Avec notre organisation :

```text
main
└── charge la configuration

router
└── distribue la configuration

handler
└── utilise la configuration
```

Chaque élément conserve une responsabilité plus claire.

---

# 7. Une première injection de dépendance

La configuration est une dépendance du handler.

Sans elle, le handler ne peut pas construire certaines données :

```go
cfg.SiteName
```

Au lieu de créer cette dépendance à l’intérieur du handler, nous la transmettons depuis l’extérieur :

```go
HomeHandler(cfg)
```

Ce principe est appelé **injection de dépendance**.

```text
Dépendance créée à l’extérieur
            ↓
transmise à la fonction qui en a besoin
```

Dans Club Manager :

```text
main crée Config
        ↓
router reçoit Config
        ↓
handler reçoit Config
```

Il ne s’agit pas nécessairement d’un framework complexe.

Une simple transmission par argument constitue déjà une forme d’injection de dépendance.

---

# 8. Conséquence sur les tests

Avant la modification, un test pouvait transmettre directement le handler :

```go
testHandler(
	t,
	"/",
	"Bienvenue",
	HomeHandler,
)
```

Après la modification, `HomeHandler` attend une configuration :

```go
func HomeHandler(cfg config.Config) http.HandlerFunc
```

Le test doit donc d’abord créer une configuration :

```go
cfg := config.Config{
	SiteName: "Club de test",
}
```

Puis construire le handler :

```go
handler := HomeHandler(cfg)
```

Ou directement :

```go
testHandler(
	t,
	"/",
	"Bienvenue sur "+cfg.SiteName,
	HomeHandler(cfg),
)
```

---

# 9. Configuration de production et configuration de test

Dans l’application réelle, la configuration provient du fichier JSON :

```go
cfg, err := config.Load("config/config.json")
```

Dans les tests des handlers, nous ne chargeons pas le fichier réel.

Nous créons directement la configuration nécessaire :

```go
cfg := config.Config{
	SiteName: "Club de test",
}
```

La distinction est importante :

```text
Application réelle
└── configuration chargée depuis un fichier

Test du handler
└── configuration créée directement dans le test
```

---

## Pourquoi ne pas appeler `config.Load` dans le test du handler ?

Le test de `HomeHandler` doit vérifier le comportement de `HomeHandler`.

Il ne doit pas également dépendre :

- du chemin du fichier ;
    
- de la présence du fichier ;
    
- de son contenu ;
    
- des droits du système de fichiers ;
    
- du bon fonctionnement de `config.Load`.
    

Sinon, plusieurs éléments seraient testés en même temps :

```text
test de HomeHandler
├── test implicite de config.Load
├── test implicite du fichier JSON
└── test du système de fichiers
```

En créant directement la structure :

```go
cfg := config.Config{
	SiteName: "Club de test",
}
```

le test reste ciblé et autonome.

---

# 10. Les données de test ne représentent pas le site réel

La valeur utilisée dans un test n’a pas vocation à représenter le véritable site.

Par exemple :

```go
cfg := config.Config{
	SiteName: "Club de test",
}
```

Cette valeur sert uniquement à vérifier le passage de l’information :

```text
"Club de test"
      ↓
Config
      ↓
Handler
      ↓
Données de vue
      ↓
Template
      ↓
Réponse HTTP
```

Une donnée volontairement différente de la valeur réelle peut même rendre le test plus pertinent.

Si le code contient encore accidentellement :

```go
"Club Manager"
```

alors qu’il devrait utiliser :

```go
cfg.SiteName
```

un test utilisant `"Club de test"` pourra détecter le problème.

---

# 11. Construire le résultat attendu avec la configuration

Un test peut construire le texte attendu à partir de la donnée injectée :

```go
func TestClubHandler(t *testing.T) {
	cfg := config.Config{
		SiteName: "Club de test",
	}

	testHandler(
		t,
		"/club",
		"Le club - "+cfg.SiteName,
		ClubHandler(cfg),
	)
}
```

Ce test vérifie que le nom reçu par le handler apparaît dans la réponse.

Il ne vérifie pas que le site porte réellement le nom `"Club de test"`.

Il vérifie le comportement suivant :

```text
la valeur de cfg.SiteName
doit être utilisée dans la page
```

---

# 12. Attention au résultat attendu

Le texte attendu par le test doit correspondre au texte réellement construit par le handler.

Si le handler produit :

```go
Title: "Le club - " + cfg.SiteName,
```

le test doit rechercher :

```go
"Le club - " + cfg.SiteName
```

et non un texte différent comme :

```go
"Présentation de " + cfg.SiteName
```

Un test doit décrire précisément le comportement attendu.

---

# 13. Adapter les tests du routeur

La signature du routeur a également changé :

```go
func New(cfg config.Config) *http.ServeMux
```

Les anciens tests utilisaient :

```go
mux := New()
```

Ils doivent maintenant fournir une configuration :

```go
cfg := config.Config{
	SiteName: "Club de test",
}

mux := New(cfg)
```

Cela concerne notamment :

- le helper des tests de routes ;
    
- le test de route inconnue ;
    
- le test de méthode interdite.
    

---

## Exemple de helper de route

```go
func testRoute(
	t *testing.T,
	route,
	expectedContent string,
) {
	t.Helper()

	cfg := config.Config{
		SiteName: "Club de test",
	}

	mux := New(cfg)

	request := httptest.NewRequest(
		http.MethodGet,
		route,
		nil,
	)

	response := httptest.NewRecorder()

	mux.ServeHTTP(response, request)

	if response.Code != http.StatusOK {
		t.Errorf(
			"statut obtenu : %d, statut attendu : %d",
			response.Code,
			http.StatusOK,
		)
	}

	body := response.Body.String()

	if !strings.Contains(body, expectedContent) {
		t.Errorf(
			"la réponse ne contient pas le texte %q ; contenu obtenu : %q",
			expectedContent,
			body,
		)
	}
}
```

---

# 14. Pourquoi les tests ont-ils cassé ?

Avant la modification :

```go
router.New()
```

Après la modification :

```go
router.New(cfg)
```

Tous les appels existants à `New()` sont devenus invalides.

Les tests ont donc signalé que certains utilisateurs de la fonction n’avaient pas encore été adaptés.

```text
changement de signature
        ↓
anciens appels incompatibles
        ↓
erreur de compilation
        ↓
adaptation des tests
```

Les tests n’étaient pas incorrects.

Ils ont joué leur rôle en révélant les endroits affectés par la modification.

# 15. Progression par petites étapes

La modification a été réalisée progressivement :

```text
1. Charger Config dans main
2. Tester l’ensemble du projet
3. Faire un commit

4. Transmettre Config au routeur
5. Adapter les tests du routeur
6. Tester l’ensemble du projet
7. Faire un commit

8. Transmettre Config à HomeHandler
9. Adapter TestHomeHandler
10. Tester l’ensemble du projet
11. Faire un commit

12. Transmettre Config à ClubHandler
13. Adapter TestClubHandler
14. Tester l’ensemble du projet
15. Faire un commit
```

Cette méthode limite le nombre de changements simultanés.

Lorsqu’un test casse, la cause est plus facile à identifier.

---

# 16. Maintenir les tests au vert

Après chaque petite étape :

```bash
go test ./...
```

L’objectif est de retrouver rapidement un état stable :

```text
tests verts
    ↓
petite modification
    ↓
tests éventuellement rouges
    ↓
adaptation du code ou des tests
    ↓
tests verts
    ↓
commit
```

Cette progression permet de construire le projet avec davantage de confiance.

---

# 17. Pourquoi faire de petits commits ?

Chaque commit représente une étape cohérente.

Exemples :

```text
Load configuration in main
```

```text
Pass configuration to router
```

```text
Use configuration in home handler
```

```text
Use configuration in club handler
```

Ces commits sont faciles à :

- comprendre ;
    
- relire ;
    
- comparer ;
    
- annuler ;
    
- expliquer ;
    
- présenter lors d’un entretien.
    

L’historique raconte progressivement l’évolution de l’architecture.

# 18. Responsabilités obtenues

Après ces modifications, les responsabilités sont mieux séparées.

## `config`

```text

```

## `main`

```text
Créer les dépendances principales
Démarrer l’application
```

## `router`

```text
Créer les routes
Distribuer les dépendances aux handlers
```

## `handlers`

```text
Recevoir une requête
Construire les données nécessaires
Appeler la vue

```

## `views`

```text
Exécuter les templates HTML
```

## `templates`

```text
Décrire la structure HTML
Afficher les données reçues
```

# 19. Erreurs fréquentes

## Charger la configuration dans chaque handler

```go
cfg, err := config.Load("config/config.json")
```

Cela mélange les responsabilités et provoque des lectures répétées du fichier.

---

## Oublier de construire le handler

Incorrect :

```go
mux.HandleFunc("GET /{$}", handlers.HomeHandler)
```

`HomeHandler` attend maintenant une configuration.

Correct :

```go
mux.HandleFunc(
	"GET /{$}",
	handlers.HomeHandler(cfg),
)
```

---

## Continuer à transmettre directement le constructeur au test

Incorrect :

```go
testHandler(
	t,
	"/",
	"Bienvenue",
	HomeHandler,
)
```

Correct :

```go
testHandler(
	t,
	"/",
	"Bienvenue sur "+cfg.SiteName,
	HomeHandler(cfg),
)
```

---

## Charger le vrai fichier dans un test de handler

À éviter :

```go
cfg, err := config.Load("../../config/config.json")
```

Préférer :

```go
cfg := config.Config{
	SiteName: "Club de test",
}
```

---

## Utiliser une donnée de test sans la vérifier

Ce test transmet une configuration :

```go
cfg := config.Config{
	SiteName: "Club de test",
}
```

mais ne vérifie qu’un texte indépendant :

```go
testHandler(
	t,
	"/club",
	"Présentation",
	ClubHandler(cfg),
)
```

Le test réussirait même si `SiteName` n’était jamais utilisé.

Il est plus pertinent de vérifier un texte construit avec la donnée :

```go
testHandler(
	t,
	"/club",
	"Le club - "+cfg.SiteName,
	ClubHandler(cfg),
)
```

# Comprendre et retenir

La configuration est chargée une seule fois au démarrage :

```text
config.Load()
```

Elle est ensuite transmise explicitement :

```text
main
  ↓
router
  ↓
handlers
```

Un handler ayant besoin de configuration devient une fonction de construction :

```go
func HomeHandler(
	cfg config.Config,
) http.HandlerFunc
```

Son utilisation devient :

```go
handlers.HomeHandler(cfg)
```

La fonction retournée conserve l’accès à `cfg` grâce à une fermeture.

Dans les tests, nous ne chargeons pas le véritable fichier JSON.

Nous créons directement une configuration adaptée au scénario :

```go
cfg := config.Config{
	SiteName: "Club de test",
}
```

La donnée de test ne représente pas nécessairement la réalité.

Elle sert à vérifier que l’information traverse correctement les différentes couches :

```text
Config
  ↓
handler
  ↓
vue
  ↓
template
  ↓
réponse HTTP
```

La règle essentielle est :

```text
Dans l’application :
charger les dépendances au démarrage.

Dans les tests :
construire directement les dépendances nécessaires.
```
