# Comprendre `t.Helper()` en Go

## Contexte

Lorsque plusieurs tests effectuent les mêmes opérations, il est possible de créer une fonction auxiliaire.

Exemple :

```go
func testHandler(
	t *testing.T,
	route string,
	expectedContent string,
	handlerToTest http.HandlerFunc,
) {
	// préparation et vérifications
}
```

Cette fonction est appelée par plusieurs tests :

```go
func TestHomeHandler(t *testing.T) {
	testHandler(
		t,
		"/",
		"Bienvenue sur Club Manager",
		HomeHandler,
	)
}
```

```go
func TestClubHandler(t *testing.T) {
	testHandler(
		t,
		"/club",
		"Présentation du club",
		ClubHandler,
	)
}
```

La fonction `testHandler` est appelée une fonction auxiliaire de test, ou test helper.

---

## Le problème sans `t.Helper()`

Imaginons le helper suivant :

```go
func testHandler(
	t *testing.T,
	expectedContent string,
	body string,
) {
	if !strings.Contains(body, expectedContent) {
		t.Errorf(
			"le contenu attendu %q est absent",
			expectedContent,
		)
	}
}
```

Et le test :

```go
func TestHomeHandler(t *testing.T) {
	testHandler(
		t,
		"Bienvenue",
		"Page indisponible",
	)
}
```

Le test échoue, car :

```text
Page indisponible
```

ne contient pas :

```text
Bienvenue
```

Sans `t.Helper()`, Go peut indiquer que l'erreur se trouve sur la ligne contenant :

```go
t.Errorf(...)
```

Par exemple :

```text
handler_helper_test.go:15:
le contenu attendu "Bienvenue" est absent
```

Cette ligne se trouve dans le helper.

Or le helper est utilisé par plusieurs tests.

Le message ne montre donc pas immédiatement quel appel du helper a provoqué l'échec.

---

## Ajouter `t.Helper()`

La fonction auxiliaire peut déclarer son rôle avec :

```go
t.Helper()
```

Exemple :

```go
func testHandler(
	t *testing.T,
	expectedContent string,
	body string,
) {
	t.Helper()

	if !strings.Contains(body, expectedContent) {
		t.Errorf(
			"le contenu attendu %q est absent",
			expectedContent,
		)
	}
}
```

`t.Helper()` indique au système de test :

> Cette fonction est un outil utilisé par un test.  
> En cas d'échec, remonte jusqu'au code qui l'a appelée.

---

## Résultat avec `t.Helper()`

Avec `t.Helper()`, le message d'erreur pointera plutôt vers l'appel :

```go
testHandler(
	t,
	"Bienvenue",
	"Page indisponible",
)
```

Par exemple :

```text
home_test.go:7:
le contenu attendu "Bienvenue" est absent
```

La ligne indiquée appartient alors à :

```go
func TestHomeHandler(t *testing.T)
```

Il devient plus facile de comprendre que l'échec concerne le test de la page d'accueil.

---

## Représentation sans `t.Helper()`

```text
TestHomeHandler
      ↓
testHandler
      ↓
t.Errorf
      ↓
Go indique la ligne située dans testHandler
```

Le message pointe vers l'outil commun, et non vers son utilisation.

---

## Représentation avec `t.Helper()`

```text
TestHomeHandler
      ↓
testHandler
      ↓
t.Helper()
      ↓
t.Errorf
      ↓
Go remonte jusqu'à TestHomeHandler
```

Le message pointe vers le test qui a utilisé le helper.

---

## Ce que fait `t.Helper()`

`t.Helper()` améliore les informations affichées lorsqu'un test échoue.

Il permet notamment de mieux identifier :

- le test concerné ;
    
- l'appel qui a transmis une mauvaise valeur ;
    
- la route testée ;
    
- le contenu attendu ;
    
- le handler utilisé.
    

Il rend donc les tests plus faciles à diagnostiquer.

---

## Ce que `t.Helper()` ne fait pas

`t.Helper()` ne :

- crée pas une fonction de test ;
    
- ne fait pas réussir le test ;
    
- ne fait pas échouer le test ;
    
- ne remplace pas `t.Error` ou `t.Errorf` ;
    
- ne modifie pas les valeurs testées ;
    
- ne corrige pas une erreur ;
    
- ne retourne pas une valeur ;
    
- ne transforme pas la fonction en méthode spéciale.
    

Il modifie principalement l'origine indiquée dans le rapport d'erreur.

---

## Où placer `t.Helper()` ?

`t.Helper()` est généralement placé au début de la fonction auxiliaire :

```go
func testHandler(
	t *testing.T,
	route string,
	expectedContent string,
	handlerToTest http.HandlerFunc,
) {
	t.Helper()

	// suite du helper
}
```

Cela indique clairement que toute la fonction est considérée comme une aide au test.

---

## Pourquoi le helper reçoit-il `t` ?

Le système de test de Go crée le `*testing.T` et le transmet au test principal :

```go
func TestHomeHandler(t *testing.T)
```

Le test transmet ensuite cette même valeur au helper :

```go
testHandler(
	t,
	"/",
	"Bienvenue",
	HomeHandler,
)
```

Le chemin est donc :

```text
go test
   ↓
crée un *testing.T
   ↓
appelle TestHomeHandler(t)
   ↓
TestHomeHandler transmet t au helper
   ↓
le helper utilise t.Helper() et t.Errorf()
```

Le helper ne crée pas lui-même un nouveau `testing.T`.

---

## Exemple avec Club Manager

```go
func testHandler(
	t *testing.T,
	route string,
	expectedContent string,
	handlerToTest http.HandlerFunc,
) {
	t.Helper()

	request := httptest.NewRequest(
		http.MethodGet,
		route,
		nil,
	)

	response := httptest.NewRecorder()

	handlerToTest(response, request)

	if response.Code != http.StatusOK {
		t.Errorf(
			"statut obtenu : %d, statut attendu : %d",
			response.Code,
			http.StatusOK,
		)
	}

	body := response.Body.String()

	if !strings.Contains(body, expectedContent) {
		t.Errorf(
			"la page ne contient pas le texte %q ; contenu obtenu : %q",
			expectedContent,
			body,
		)
	}
}
```

Les tests peuvent ensuite utiliser ce helper :

```go
func TestHomeHandler(t *testing.T) {
	testHandler(
		t,
		"/",
		"Bienvenue sur Club Manager",
		HomeHandler,
	)
}
```

```go
func TestClubHandler(t *testing.T) {
	testHandler(
		t,
		"/club",
		"Présentation du club",
		ClubHandler,
	)
}
```

---

## Exemple d'échec

Supposons que `HomeHandler` retourne :

```text
Page indisponible
```

alors que le test attend :

```text
Bienvenue sur Club Manager
```

Le helper exécute :

```go
t.Errorf(
	"la page ne contient pas le texte %q ; contenu obtenu : %q",
	expectedContent,
	body,
)
```

Grâce à :

```go
t.Helper()
```

Go indique l'appel effectué dans :

```go
TestHomeHandler
```

plutôt que la ligne générique située dans `testHandler`.

---

## Plusieurs niveaux de helpers

Un helper peut appeler un autre helper.

Exemple :

```go
func testHandler(t *testing.T) {
	t.Helper()

	checkStatus(t)
}
```

```go
func checkStatus(t *testing.T) {
	t.Helper()

	t.Errorf("statut incorrect")
}
```

Si les deux fonctions sont déclarées comme helpers, Go remonte jusqu'au premier appel qui n'est pas un helper.

```text
Test principal
     ↓
premier helper
     ↓
deuxième helper
     ↓
erreur
     ↓
message associé au test principal
```

Chaque fonction auxiliaire concernée doit donc appeler :

```go
t.Helper()
```

---

## Quand utiliser `t.Helper()` ?

Il est utile dans les fonctions qui :

- préparent des données pour plusieurs tests ;
    
- créent des requêtes HTTP de test ;
    
- vérifient un résultat commun ;
    
- comparent des valeurs ;
    
- créent des fichiers temporaires ;
    
- initialisent une base de données de test ;
    
- exécutent des vérifications réutilisables.
    

Exemple simple :

```go
func assertEqual(
	t *testing.T,
	got string,
	want string,
) {
	t.Helper()

	if got != want {
		t.Errorf(
			"valeur obtenue : %q, valeur attendue : %q",
			got,
			want,
		)
	}
}
```

---

## Quand ne pas l'utiliser ?

`t.Helper()` n'est généralement pas nécessaire dans une fonction de test principale :

```go
func TestHomeHandler(t *testing.T) {
	// test principal
}
```

Cette fonction représente déjà le test que Go doit afficher.

Il n'est donc pas utile d'écrire :

```go
func TestHomeHandler(t *testing.T) {
	t.Helper()
}
```

Cela pourrait même rendre le rapport d'erreur moins clair, puisque Go tenterait de remonter au-delà du test principal.

---

## Helper et nom de fonction

Une fonction de test principale commence par :

```go
Test
```

Exemple :

```go
func TestHomeHandler(t *testing.T)
```

Un helper porte généralement un nom commençant par une minuscule :

```go
func testHandler(t *testing.T)
```

ou :

```go
func checkHandlerResponse(t *testing.T)
```

Le helper ne doit pas respecter la signature spéciale des tests principaux.

Il est appelé manuellement par les tests.

---

## Helper et fichier `_test.go`

Un helper utilisé uniquement par les tests doit être placé dans un fichier se terminant par :

```text
_test.go
```

Exemple :

```text
internal/
└── handlers/
    ├── 001_home.go
    ├── 001.1_home_test.go
    └── 005_helper_handler_test.go
```

Ainsi, le helper :

- est disponible pendant les tests ;
    
- ne fait pas partie du programme normal ;
    
- reste proche du code testé.
    

---

## Commenter un helper

Un helper peut devenir difficile à comprendre lorsqu'il reçoit plusieurs paramètres.

Il est utile de documenter :

- ce qu'il teste ;
    
- le rôle de chaque étape ;
    
- ce qu'il ne teste pas ;
    
- la raison de l'utilisation de `t.Helper()`.
    

Exemple :

```go
// testHandler vérifie le comportement commun
// des handlers HTTP simples.
//
// Il simule une requête GET, exécute directement
// le handler, puis vérifie le statut et le contenu.
//
// Il ne vérifie pas que la route est correctement
// enregistrée dans le routeur.
func testHandler(
	t *testing.T,
	route string,
	expectedContent string,
	handlerToTest http.HandlerFunc,
) {
	t.Helper()

	// suite du helper
}
```

---

## Comprendre et retenir

`t.Helper()` indique qu'une fonction est un outil utilisé par un test.

```go
func testHandler(t *testing.T) {
	t.Helper()
}
```

Sans `t.Helper()` :

```text
l'erreur pointe vers le code du helper
```

Avec `t.Helper()` :

```text
l'erreur pointe vers le test qui a appelé le helper
```

`t.Helper()` ne change pas le résultat du test.

Il améliore uniquement le diagnostic en cas d'échec.

La phrase à retenir est :

> `t.Helper()` dit à Go : « Cette fonction aide le test. En cas d'erreur, montre plutôt l'endroit où elle a été appelée. »


Remarque : 

## `t.Helper()` est propre aux tests


```go
t.Helper()
```

est spécifique aux tests, car `t` est un :

```go
*testing.T
```

La méthode `Helper()` appartient au type `testing.T`.

Elle indique à Go que la fonction courante est une fonction auxiliaire **de test** :

```go
func testHandler(t *testing.T, ...) {
	t.Helper()

	// vérifications
}
```

Elle sert à améliorer l’emplacement indiqué lorsqu’un test échoue.

Une fonction helper normale n’utilise donc pas `t.Helper()` :

```go
func fullName(firstName, lastName string) string {
	return firstName + " " + lastName
}
```

Il n’y a pas de `*testing.T`, puisqu’elle ne travaille pas avec le système de tests.

## Un helper doit-il forcément être réutilisé ?

Pas obligatoirement, mais il devient surtout pertinent lorsqu’il :

- évite une répétition ;
- donne un nom clair à une opération ;
- simplifie une fonction complexe ;
- isole une responsabilité précise.

Il ne faut toutefois pas transformer chaque ligne en helper. Une fonction auxiliaire est utile lorsqu’elle rend le code **plus simple à lire**, et non lorsqu’elle ajoute seulement un niveau supplémentaire.

La phrase à retenir est :

> Un helper est une fonction qui aide une autre fonction. `t.Helper()` est seulement la manière de déclarer un helper dans le contexte particulier des tests.
